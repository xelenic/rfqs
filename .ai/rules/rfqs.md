# Rfqs

## Sourcing has no Return to Senior Operations
Since 2026-10-12, only Admin can send a Sourcing part back to Senior Operations (the 'sourcing_to_ops' kind of _complete_button, RfqController::returnSeniorOps()), recorded as the part's member. Every spot that shows it, and the controller, gate on User::canSendSourcingPartsBackToSeniorOps(). Don't show it to Sourcing again without the business asking.

## RFQ progress chart: HTML cards and SVG lines, no ECharts
Since 2026-10-16, renderRfqProgressChart (public/js/admin.js) draws the RFQ page's Progress chart itself instead of using ECharts. Columns follow tree depth, there is one row per lane, and each parent is centred on its children. Every node is an HTML card (.pc-node) with a round picture overlapping its left edge, connected by SVG curves. Each node in #rfq-progress-data (built in show.blade.php) carries: name, role, step, rfq_number, meta[0..1], state (done/current/pending/returned), icon (from $stepTabs) and person. person is null for nobody, ['masked' => true] when the name must stay hidden (show a lock), or name/photo/initial. Masking stays server-side, so hidden names never reach the page. Build card text with textContent, never innerHTML.

## Sourcing's My Pending RFQs: three tabs
Since 2026-10-16, a Sourcing member's My Pending RFQs has three tabs, part by part. **Pending for Sourcing** ($rfqs, data-de-tab="todo", the default) lists parts still with them (completed_at and returned_at null) and parts Data Entry sent back to finalize (RfqAssignment::whereAwaitingFinalize()). **With Data Entry** (?tab=with-data-entry, $withDataEntryRfqs) lists parts with completed_at set and data_entry_completed_at null; it shows Not started / In progress / Paused and whom it was assigned to, but never who in Data Entry started it. **Finalized** (?tab=finalized, $finalizedRfqs) lists finalized parts on Pending RFQs, with RfqAssignment::stageAfterFinalize(). Data Entry returns stay on Returns. Each tab has its own paginator and count ($sourcingCounts). The open tab is kept in ?tab= via data-de-tab / data-tab-default and #deTabInput. Keep the controller queries, the row loops' @continue checks and the sidebar badge (Pending for Sourcing = open + Rfq::awaitingFinalizeCount()) in step. Admin's _sourcing_overview has a single list.

## Senior Operations' Approve verifies line items first (_senior_ops_approve_modal)
Since 2026-10-19, every Senior Operations Approve opens _senior_ops_approve_modal through _senior_ops_approve_button; never a plain form. That covers a part on the Review list (approvePart) and the whole RFQ on the list's fallback row and the RFQ page. For each part it approves, the popup shows Line Items to Add, Line Items Added and Difference, read only, from RfqAssignment::lineItemsCheck(), and asks for Actual Line Items (actual_line_items[part]). RfqController::verifiedLineItems() requires one for every part, a whole number from 0 to MAX_DATA_ENTRIES, for approveSeniorOpsPart() and completeSeniorOpsReview() (Rfq::partsAwaitingSeniorOpsApproval()). It's kept as rfq_user.verified_line_items. Read it with verifiedLineItems(): returns are not cleared, so the value only counts while the part is Senior-Ops-approved. Pass the part as approvePart, never $part, which show.blade.php already uses.

## Add RFQ: WC is fixed, only the four digits are typed
Since 2026-10-20, while Settings → WC Validation is on (Setting::wcFormatRequired()), the Add RFQ form's WC Number has "WC" fixed in an input-group, and the field takes only four digits. admin.js (.js-wc-digits) strips anything else, so a pasted "WC0123" becomes "0123". The field has no maxlength, because a maxlength would cut a paste before the script strips it. RfqController::store() calls wcNumberChecked(..., digitsOnly: true), which saves "0123" as WC0123 and still accepts a whole "WC0123". The Edit form keeps the whole WC0000 field, so older numbers can stay. With the setting off, both forms are free text.

## @mentions: all active staff, with roles and pictures
Since 2026-10-20, anyone active can be @mentioned in an RFQ comment: RfqComment::mentionableUsers(), looked up once per request and kept on the request's attributes, not once(). The dropdown reads RfqComment::mentionDirectory() from show.blade.php's #rfq-mention-users JSON (id, name, role, avatar, initial; json_encode with the JSON_HEX flags). admin.js builds each item with the person's photo or initial and their roles, and matches what's typed against name or role. bodyWithMentions() highlights in one regex pass, longest names first and whole names only. Pass it mentionableUsers(), never a role's members, so highlighting matches the dropdown and the mention messages.

## Sourcing and Data Entry see only their own part of an RFQ's timeline
Since 2026-10-20, the RFQ page renders Rfq::activityTimelineFor(auth()->user()), never activityTimeline() directly. Someone in Sourcing and/or Data Entry with no other role (User::seesOnlySourcingAndDataEntryTimeline()) gets three things. Lifecycle events: only Rfq::SOURCING_AND_DATA_ENTRY_TIMELINE_TYPES. Action comments: only those whose author is in Sourcing or Data Entry; plain comments and replies stay, since they're the shared discussion (RfqComment::isForSourcingAndDataEntry()). Alerts: only those sent to someone in Sourcing or Data Entry. No other role's reviews, approvals, rejections, holds, reassignments or GM Assistant actions. The header's comment count counts what they see. _rfq_detail_modal's thread applies the same comment filter. Everyone else, Admin and anyone holding another role included, sees everything.

## Closed RFQs: no created or closed details for Sourcing and Data Entry
Since 2026-10-20, someone in Sourcing and/or Data Entry alone (User::seesOnlySourcingAndDataEntryTimeline()) doesn't see when a closed RFQ was made or closed, by whom, or its quotation number. On the Closed RFQs list ($hidesCreatedAndClosed in index.blade.php), the Created and Closed columns are left out: _rfq_row takes showCreated and showClosed, and _closed_part_rows takes showCreatedAndClosed, with the colspan adjusted. On a closed RFQ's page, the details card leaves out Created by, Created and Quotation number. Their step tabs and timeline already leave out the Created and Closed steps. Everyone else, and an open RFQ, are unchanged.

## Head of BD's Approve finalizes line items, which drive GM Assistant's target
Since 2026-10-20, every Head of Business Development Approve opens _head_of_bd_approve_modal through _head_of_bd_approve_button ($approvePart for a part, or null for the whole RFQ). The popup shows to add, added and Senior Ops' verified count read only, and asks for Finalized Line Items (finalized_line_items[part]). RfqController::finalizedLineItems() requires one for every part (it shares lineItemsGiven() with the Senior Ops check). They're kept as rfq_user.finalized_line_items; read them with finalizedLineItems(), which is null unless the part is Head-approved, since returns don't clear the column. Rfq::gmAssistantLineItemsFor() prefers them (source 'finalized'), and gmAssistantTargetBreakdown() then always goes per line item, even with Settings' per-line-item switch off, as Data Entry's line items to add do. Senior Operations' Actual Line Items never drive it; the user confirmed that on 2026-10-24 after briefly asking for Actual. Both line-item popups are .js-line-items-modal with data-field; admin.js fills any read-only box by its data-value key.

## Sourcing's Finalize asks for Submitted Line Items (_finalize_modal)
Since 2026-10-24, Sourcing's Finalize (_finalize_button) opens _finalize_modal, never a plain form. It is laid out like Verify line items: to add, added, difference (read only, RfqAssignment::lineItemsCheck()), the line items history, and a required Submitted Line Items field (submitted_line_items[part]). RfqController::finalize() validates it with lineItemsGiven(), and Rfq::finalizePart($part, $submitted) saves it as rfq_user.submitted_line_items. Read it with submittedLineItems(), which is null unless the part is finalized, because returns don't clear the column. lineItemsCheck() includes 'submitted', so Senior Operations' and the Head of BD's popups show it read only. lineItemsHistory() adds a 'submitted' row, and the verified row compares against it. Any page with a Finalize button must include _finalize_modal next to _complete_modal (index, show, the Sourcing dashboard). Hidden redirect fields use data-from-button, and Back to a parent popup uses data-back-modal with .js-li-back; both are handled by the shared .js-line-items-modal script in admin.js.

## GM Assistant's Time Left explains itself on hover (_gm_assistant_time_card)
Since 2026-10-24, every GM Assistant Time Left has a popup: on their list (running, paused or not started) and on their dashboard's waiting list. The trigger is wrapped in span.countdown-explained[data-hover-card], and the shared hover-card popover in admin.js renders the <template> from _gm_assistant_time_card. Its data comes from Rfq::gmAssistantTimeExplained($part): which count the line items are, who gave it in which role and when, the time per line item, the target or the priority target, the state, and the time used and left. The badge inside has no title (_countdown_badge 'hoverCard' => true; the ticker removes titles inside a hover card). On show, syncCountdown() copies the ticking badge's label, used time and off-hours state into [data-countdown-left|used|off-hours]. Keep the explanation in gmAssistantTimeExplained(), so it always matches gmAssistantTargetSeconds().

## A split part's "View details" opens the RFQ focused on that part
Since 2026-10-25, any link from a row or line that stands for one part of a split RFQ uses Rfq::detailsUrl($part, $status), which adds ?part= only when the RFQ is split. This covers the per-part list rows, closed part rows, the quick view's Open full RFQ, the Sourcing overview, and the dashboards and critical monitor via each entry's 'part' key. On show.blade.php, ?part= sets $focusPart, and the progress chart keeps only that part's Sourcing branch ($chartPart), with a "RFQ…-P2 of P3 only" badge. An Admin gets a This part / Whole RFQ switch (?flow=whole); every other role always sees the part they came from. A whole-RFQ row (fallback rows, Returns, All RFQs) links without a part. Use detailsUrl() for any new per-part link rather than route('admin.rfqs.show').

## RFQ page on one part ($pagePart): every part-related section follows it
Since 2026-10-25 the part focus covers the whole RFQ page, not just the chart. $pagePart is set at the top of show.blade.php from ?part= (and cleared by ?flow=whole, Admin only). $inPage/$pageAssignees narrow every per-part section: the top-bar parts (Assign to Data Entry, Finalize, GM Assistant parts), $stepDone/$currentStep/$stepPartsDone (from that part's pivot), the step panels (_step_parts reads $pagePart), the Assigned Sourcing card, the stopped-part banner, quotation numbers, Data Entry returns, the timeline (Rfq::activityTimelineFor($viewer, $part) via timelineEntryPart(); the RFQ's own steps and plain comments stay — since 2026-10-27 its 'rejected' step carries the part of the rejection's comment, so another part's rejection stays off, and the step panels' Rejected details show only when $rejectionInPage) and Time spent (Rfq::timeSpent(part:)). Decisions become the part's own ($partDecision: approve-*-part, reject with data-part, close the part, hold or cancel the part), never the whole RFQ's, which would decide every part. The title is that part's number, and the banner [data-part-flow] says what's shown. RFQ-level details (subject, WC, description) and the discussion stay whole. A new per-part section must filter by $pagePart.

## Assign Sourcing picks people from a searchable dropdown that recommends by job category
Since 2026-10-26, at the user's request, step 3 of the Assign Sourcing wizard has a searchable dropdown for each part instead of a <select>. The data comes from the #assign-sourcing-people JSON: id, name, avatar, initial, pending (withSourcingWorkloadCounts), and categories (User::jobCategories(), which both RfqController queries eager-load). What is picked is a hidden assignments[part]. People tagged with the RFQ's category (an exact, case-insensitive name match, since rfqs.category is a string) are marked Recommended, highlighted green and listed first. #assign-recommend-note names them, or says nobody is tagged yet. The one shared panel (#assign-person-panel) sits outside .modal-dialog but inside the modal, with position: fixed. This keeps the scrollable body from clipping it and keeps its search box inside Bootstrap's focus trap.
